\noindent Each item is labelled \NEW{} (genuinely new; requires committee vote)

\vspace{0.4em}
\noindent\textit{SIDS changes:}
\begin{enumerate}[nosep,leftmargin=1.5em]
  \item \NEW{} \textbf{\texttt{LagrangeControlPointDistribution\_t} enum.}
    Records the parametric-space distribution of Lagrange control points.
    Values: \texttt{GaussLobattoLegendre}, \texttt{Equidistant},
    \texttt{GaussLegendre}, \texttt{WarpAndBlend}.
    Stored as an optional named child of \texttt{ElementInterpolation\_t}
    or \texttt{SolutionInterpolation\_t}; required for
    \texttt{ParametricLagrange}.
    \textit{Rationale:} a reader cannot reconstruct basis functions from
    control-point positions alone without this information.

  \item \CLARIFY{} \textbf{\texttt{GridLocation = InterpolationPoints}.}
    Designates \texttt{InterpolationPoints} as the required
    \texttt{GridLocation} for whole-zone high-order \texttt{FlowSolution\_t}
    nodes. \texttt{CellCenter} with \texttt{PointRange}/\texttt{PointList}
    remains the convention for variable-order (p-adaptive) subsets, as
    implied by v2.

  \item \CLARIFY{} \textbf{\texttt{InterpolationOrders} encoding.}
    Formalises the on-disk representation of \texttt{SpatialOrder} and
    \texttt{TemporalOrder} as a 2-element \texttt{IndexArray\_t} child of
    \texttt{FlowSolution\_t}.  Information content is identical to v2.

  \item \NEW{} \textbf{Mandatory coordinate normalisation for Cartesian modal.}
    Requires normalisation by the maximum inter-vertex distance $h^e$, which
    must be stored alongside modal coefficients.
    \textit{Rationale:} high-order monomials in un-normalised physical
    coordinates cause catastrophic floating-point overflow at large or small
    element sizes.
\end{enumerate}

\section{Motivation and Scope}
%% ═════════════════════════════════════════════════════════════════════════

\begin{v2quote}
The aim is to cater for the large diversity of high-order methods by including a specification of
the interpolation spaces for solutions in the file, fixing the bare essentials: the coordinate
system.  The choice of Lagrangian interpolation spaces is applicable to the mesh as well as the
solution description.  This generalisation will:

\begin{itemize}[leftmargin=2em]
  \item allow accurate representation of data in a range of popular interpolation spaces which
    could otherwise only be approximated;
  \item allow use of the native storage of the application for the Lagrangian description, leading
    furthermore to
    \begin{itemize}
      \item a simpler, more robust, and generic implementation of drivers;
      \item more efficient I/O by straightforwardly dumping data blocks;
      \item avoiding loss of precision for very specific point distributions;
    \end{itemize}
  \item avoid the need to redefine the format for each new interpolation type/order;
  \item cater for space-time methods as well as for ALE computations by including time in the
    functional expressions.
\end{itemize}

Currently it is assumed that high-order intra-element interpolation is \emph{restricted to
unstructured mesh computations}, as structured meshes do not offer the possibility to
individually list elements per order and moreover do not support curved elements.  Both modal and
nodal interpolations are supported.

There is clear potential for future extension via an explicit specification of mathematical
expressions of the individual interpolation functions.  This will increase the flexibility for
modal interpolation approaches.
\end{v2quote}


%% ═════════════════════════════════════════════════════════════════════════
\section{Rationale}
%% ═════════════════════════════════════════════════════════════════════════

\begin{v2quote}
This proposal lifts the limitation of fixing the interpolation functions implicitly by imposing
the position of Lagrange control points as proposed for geometric interpolation/curved elements in
CPEX~0036 and CPEX~0038.  Instead, the description of the functional space and its interpolant is
integrated as metadata in the CGNS file in order to allow high flexibility as to the choice of
interpolants or even coordinates, an automatic procedure to allow for very high interpolation
order, and time-dependent interpolants.
\end{v2quote}


%% ═════════════════════════════════════════════════════════════════════════
\section{Extension of the SIDS}
%% ═════════════════════════════════════════════════════════════════════════

\subsection{Conventions}

\begin{v2quote}
\textbf{Modifications to the SIDS:}
\begin{itemize}
  \item addition of a new section~3.4: \emph{High-order interpolation}.
\end{itemize}

In the remainder of this section we introduce the different paragraphs (with numbering to be
adapted) that should be added to the new section.
\end{v2quote}

\begin{v2quote}
The CGNS standard allows the user to specify their own interpolation approach for both elements
and solution.  The basic principles are:
\begin{enumerate}
  \item The element coordinate system per element type is a fixed convention.
  \item For the solution interpolation per each element type and interpolation order, a separate
    interpolation block is added which provides one of three choices:
    \begin{itemize}
      \item the set of control points for Lagrange interpolants;
      \item the maximum degree of a Pascal polynomial space defined in parametric coordinates;
      \item the maximum degree of a Pascal polynomial space defined in Cartesian
        (non-parametric) coordinates.
    \end{itemize}
    The first two cover parametric interpolation, whereas the last covers
    modal/Cartesian interpolation.
  \item The mesh is always defined using interpolations in parametric space, by specifying the
    set of control points.  The standard will only allow element types defined up to now, in
    order not to modify the element connectivity description.
  \item The interpolation is \emph{not} supposed to be the same for the geometry as for the
    solution, unless explicitly specified that way.
  \item In addition to the spatial coordinates, time can also be used as an independent variable.
\end{enumerate}
The following sections describe how interpolations are specified.
\end{v2quote}

% ─────────────────────────────────────────────────────────────────────────
\subsubsection{Interpolation Type Enumeration: \texttt{InterpolationType\_t}}
\label{sec:interpolation-type}
% ─────────────────────────────────────────────────────────────────────────

\begin{v2quote}
\texttt{InterpolationType\_t} specifies how the high-order interpolants for the solution are
defined.  \texttt{InterpolationType\_t} can take four values:

\begin{itemize}
  \item \textbf{\texttt{ParametricLagrange}} corresponds to a Lagrange interpolation based upon a
    set of specified control point coordinates in parametric space for a standard interpolation
    space.
  \item \textbf{\texttt{ParametricMonomialsPascal}} corresponds to modal interpolation functions
    in parametric coordinates, based on monomials according to the classical Pascal sets.
  \item \textbf{\texttt{CartesianMonomialsPascal}} corresponds to modal interpolation functions
    in a Cartesian coordinate system, centred on the element and parallel to the main axes.  The
    interpolation functions are based on monomials according to the classical Pascal sets.
  \item \textbf{\texttt{IsoParametric}} corresponds to using the same interpolation functions for
    the solution as for the mesh.
\end{itemize}
\end{v2quote}

% ─────────────────────────────────────────────────────────────────────────
\subsubsection{Lagrange Control Point Distribution}
\label{sec:lagrange-distribution}
% ─────────────────────────────────────────────────────────────────────────

For \texttt{ParametricLagrange} interpolation to be unambiguous and interoperable, the
distribution of control points in parametric space must be explicitly recorded.  Without
this, a writer using Gauss--Lobatto--Legendre (GLL) points and a reader assuming equidistant
points (or vice-versa) produce $O(1)$ interpolation error --- catastrophic, not a small
numerical error.

\paragraph{Required attribute: \texttt{LagrangeControlPointDistribution}.}
A \texttt{DataArray\_t} of \texttt{Character} type, child of \texttt{ElementInterpolation\_t}
or \texttt{SolutionInterpolation\_t} when \texttt{InterpolationType} is
\texttt{ParametricLagrange}.  Allowed values:

{\sloppy
\begin{itemize}
  \item \textbf{\texttt{GaussLobattoLegendre}} (recommended default): 1D points are roots of
    $(1-u^2)\,P_p'(u)=0$, where $P_p$ is the Legendre polynomial of degree~$p$; includes
    endpoints $u_0 = -1$, $u_p = +1$.  Optimal conditioning and quadrature accuracy.
  \item \textbf{\texttt{Equidistant}}: $u_i = -1 + 2i/p$.  Simple uniform spacing; discouraged
    for $p>7$ due to poor conditioning of the Vandermonde matrix.
  \item \textbf{\texttt{GaussLegendre}}: 1D points are roots of $P_p(u)=0$; does \emph{not}
    include the endpoints.  Rarely used for element interpolation.
  \item \textbf{\texttt{WarpAndBlend}} (simplices only): specialised distribution for triangles
    and tetrahedra ensuring well-conditioned Vandermonde matrices~\cite{Warburton06}.
\end{itemize}
\par}

\paragraph{Multi-dimensional construction.}
For tensor-product elements (\texttt{QUAD}, \texttt{HEXA}), the chosen 1D distribution is
applied independently in each parametric direction.  For simplex elements (\texttt{TRI},
\texttt{TETRA}), \texttt{WarpAndBlend} or Fekete distributions are required for $p>2$;
equidistant points may be used at $p=2$ but become unstable at higher orders.

\paragraph{Default behaviour.}
If \texttt{LagrangeControlPointDistribution} is absent, an implementation \emph{should} assume
\texttt{GaussLobattoLegendre} but \emph{should} issue a warning to flag the ambiguity.  Strict
CPEX-0045 conformance requires the attribute to be present.

% ─────────────────────────────────────────────────────────────────────────
\subsubsection{New \texttt{GridLocation\_t} Value: \texttt{InterpolationPoints}}
\label{sec:interpolation-points-loc}
% ─────────────────────────────────────────────────────────────────────────

CPEX-0045 adds a new \texttt{GridLocation\_t} enumeration value:
{\sloppy
\begin{itemize}
  \item \textbf{\texttt{InterpolationPoints}} (enum value $9$): the
    \texttt{FlowSolution\_t} data is stored at the control points (Lagrange) or as
    coefficients (modal) defined by the associated \texttt{SolutionInterpolation\_t} node in
    the family.  The \texttt{DataArray\_t} size for each field is
    $N_\mathrm{elements} \times N_\mathrm{DOFs/element}$, where
    $N_\mathrm{DOFs/element}$ depends on the interpolation type and orders.
    Coefficients for all DOFs of element~0 are stored contiguously, followed by all DOFs of
    element~1, and so on.
\end{itemize}
\par}

\paragraph{Mandatory for high-order solutions.}
For uniform-order high-order solutions covering all elements of an unstructured zone,
\texttt{GridLocation = InterpolationPoints} is mandatory.  Reusing
\texttt{GridLocation = CellCenter} for high-order data is incorrect: \texttt{CellCenter}
mandates an array of size equal to the number of cells, which contradicts the
$N_\mathrm{elements} \times N_\mathrm{DOFs/element}$ requirement of high-order data and will
cause failures in standard CGNS readers.

\paragraph{When \texttt{CellCenter} is still appropriate.}
\texttt{CellCenter} combined with \texttt{PointRange} or \texttt{PointList} remains valid for
\emph{variable-order} configurations (Section~\ref{sec:variable-order}), where each
\texttt{FlowSolution\_t} block describes a subset of cells at a specific order and the
solution values are interpreted per the block's \texttt{InterpolationOrders} child.

\paragraph{Discontinuous vs.\ continuous methods.}
Discontinuous Galerkin (DG) methods, where each element carries its own independent DOFs,
always use \texttt{InterpolationPoints}.  Continuous Galerkin (CG) methods that share DOFs
across element boundaries are implementation-defined: some codes still use
\texttt{InterpolationPoints} with duplicated boundary values, others use
\texttt{Vertex} with a global DOF numbering.

% ─────────────────────────────────────────────────────────────────────────
\subsubsection{Parametric Interpolation by Specification of Lagrange Control Points}
\label{sec:lagrange}
% ─────────────────────────────────────────────────────────────────────────

\begin{v2quote}
\textbf{Scope}: Both solution and element shape can be specified using this formulation.  For
elements, this convention allows redefinition of the position and order of the control points with
respect to the standard definitions for each \texttt{ElementType\_t} described in Section~\ref{sec:coord-systems}.
The standard definition continues to be used when no interpolation is explicitly introduced.

Lagrange interpolants require, next to the specification of control point locations, also the
specification of the standard function space $\mathcal{V}$.  Its cardinality $N$ defines the
number of control points that need to be specified.

We denote the Lagrange interpolant corresponding to control point $\mathbf{u}_i$ as
$\lambda_i$$^{1}$.  Furthermore, we need an arbitrary set of base functions for $\mathcal{V}$, such
that $\mathcal{V} = \mathrm{span}(\psi_j,\; j = 0\ldots N-1)$.  The Lagrange interpolants are
then found as a linear combination of the base functions
%
\begin{equation}
  \lambda_i(\mathbf{u}) = \sum_j V^{-1}_{ij}\, \psi_j(\mathbf{u})
\end{equation}
%
using the inverse of the Vandermonde matrix $V$ associated to the control points $\mathbf{u}_i$
and the basis $\psi$,
%
\begin{equation}
  V_{ij} = \psi_j(\mathbf{u}_i).
\end{equation}

The (spatial) parametric function spaces $\mathcal{V}_p(u,v,w)$ for each element type and order
$p$, which support the Lagrange-type interpolation, are listed in Table~\ref{tab:spaces}.  Next
to the standard ``complete'' element, also incomplete, or so-called serendipity elements are
supported in higher dimensions.  A first type of serendipity element only specifies control
points on the edges.  In three-dimensional elements of sufficient order, a second serendipity
interpolation can be defined which only excludes control points internal to the element.
\end{v2quote}

\begin{v2quote}
\noindent In which we use direct sums $\oplus$ and products $\otimes$ of the following standard spaces:

\begin{itemize}
  \item The linear space: $\Lsp(u) = \mathrm{span}\{u^i,\; 0 \le i \le p\}$

  \item Tensor product spaces, $N = (p+1)^d$:
  \begin{align*}
    \Qtp(u,v)      &= \Lsp(u) \otimes \Lsp(v)      = \mathrm{span}\{u^i v^j,\; 0 \le i,j \le p\} \\
    \Qthp(u,v,w)   &= \Lsp(u) \otimes \Lsp(v) \otimes \Lsp(w)
                    = \mathrm{span}\{u^i v^j w^k,\; 0 \le i,j,k \le p\}
  \end{align*}

  \item Pascal triangle/tetrahedron, $N = \frac{(p+1)\cdots(p+d)}{d!}$:
  \begin{align*}
    \Ptp(u,v)      &= \mathrm{span}\{u^i v^j,\; 0 \le i+j \le p\} \\
    \Pthp(u,v,w)   &= \mathrm{span}\{u^i v^j w^k,\; 0 \le i+j+k \le p\}
  \end{align*}
\end{itemize}

For space-time function spaces (e.g.\ ALE meshes), the complete functional space is given by
%
\begin{equation}
  \Vpq(u,v,w,t) = \mathcal{V}_p(u,v,w) \otimes \mathcal{L}_q(t)
\end{equation}
%
where $p$ and $q$ are the spatial and temporal orders respectively.
\end{v2quote}

\paragraph{Prism (\texttt{PENTA\_6}) ordering convention.}
The prism space $\Ptp(u,v)\otimes\Lsp(w)$ is a tensor product of a triangle in $(u,v)$ and a
line in $w$.  The implementation requires the line direction $w$ to vary \emph{slowest} when
enumerating control points:  for each line node along $w$ ($w$-major), enumerate the
$(p+1)(p+2)/2$ triangle nodes in $(u,v)$.  This is \emph{not} a simple 3D tensor product like
\texttt{HEXA}.

\paragraph{Pyramid (\texttt{PYRA\_5}) cardinality.}
Following Bergot--Cohen--Duruflé~\cite{BCD10}, the cardinality of the pyramid functional space
at order $p$ is
\begin{equation}
  N_\mathrm{PYRA}(p) = \frac{(p+1)(p+2)(2p+3)}{6},
\end{equation}
giving $5$, $14$, $30$, $55$ for $p=1,2,3,4$ respectively.  These are the values returned by
\texttt{cg\_element\_lagrange\_interpolation\_size} and consume the corresponding
\texttt{ElementType\_t} tags \texttt{PYRA\_5}, \texttt{PYRA\_14}, \texttt{PYRA\_30},
\texttt{PYRA\_55}.  The control-point layout convention is the user's responsibility; the
library does not provide a built-in pyramid layout helper.

% ─────────────────────────────────────────────────────────────────────────
\subsubsection{Parametric Modal Interpolation}
\label{sec:parametric-modal}
% ─────────────────────────────────────────────────────────────────────────

\begin{v2quote}
\textbf{Scope}: This type of interpolation only applies to solutions.
\end{v2quote}

\begin{v2quote}
For solutions, modal interpolation is also allowed.  The interpolation functions are based on an
ordered set of monomials spanning the Pascal spaces.  The cardinality of the modal basis is the
same for every element shape of a given dimension --- the binomial coefficient
\begin{equation}
  N_\mathrm{modal} = \binom{p+d}{d}, \qquad d = \text{element dimension}, \quad p = \text{spatial order}
\end{equation}
For space-time interpolation the cardinality is multiplied by $(q+1)$ where $q$ is the temporal
order.  Consequently a \texttt{QUAD\_9} element used with order-2 modal interpolation stores
$\binom{4}{2} = 6$ monomial coefficients (not 9 --- 9 is the Lagrange-basis cardinality of the
tensor-product space $\Qtp$).  The helper functions \texttt{cg\_element\_monomial\_size} and
\texttt{cg\_solution\_monomial\_size} return $N_\mathrm{modal}$ for any supported element type
and order combination.

According to the underlying dimension the monomials are given by:

\begin{itemize}
  \item 1D: the monomials $1, u, u^2, u^3, \ldots, u^p$

  \item 2D --- Pascal triangle ordered as:
\begin{lstlisting}[language=C,numbers=none]
for (int i=0; i<=p; i++)
    for (int j=0; j<=i; j++)
        f[idx++] = u^(i-j) * v^j;
\end{lstlisting}

  \item 3D --- Pascal tetrahedron ordered as:
\begin{lstlisting}[language=C,numbers=none]
for (int i=0; i<=p; i++)
    for (int j=0; j<=i; j++)
        for (int k=0; k<=i-j; k++)
            f[idx++] = u^(i-j-k) * v^k * w^j;
\end{lstlisting}
\end{itemize}

The above covers purely spatial interpolation.  For space-time function spaces the complete
functional spaces are given by multiplying by monomials in (parametric) time $\tau$:

\begin{itemize}
  \item 1D in space plus time:
\begin{lstlisting}[language=C,numbers=none]
for (int h=0; h<=q; h++)
    for (int i=0; i<=p; i++)
        f[idx++] = tau^h * u^i;
\end{lstlisting}

  \item 2D in space plus time:
\begin{lstlisting}[language=C,numbers=none]
for (int h=0; h<=q; h++)
    for (int i=0; i<=p; i++)
        for (int j=0; j<=i; j++)
            f[idx++] = tau^h * u^(i-j) * v^j;
\end{lstlisting}

  \item 3D in space plus time:
\begin{lstlisting}[language=C,numbers=none]
for (int h=0; h<=q; h++)
    for (int i=0; i<=p; i++)
        for (int j=0; j<=i; j++)
            for (int k=0; k<=i-j; k++)
                f[idx++] = tau^h * u^(i-j-k) * v^k * w^j;
\end{lstlisting}
\end{itemize}
\end{v2quote}

\begin{v2quote}
Note that this space-time formulation reverts to purely spatial interpolation --- including the
ordering --- for the (default) temporal order $q=0$.
\end{v2quote}

% ─────────────────────────────────────────────────────────────────────────
\subsection{Cartesian Modal Interpolation}
\label{sec:cartesian-modal}
% ─────────────────────────────────────────────────────────────────────────

\begin{v2quote}
\textbf{Scope}: Cartesian modal interpolation only applies to solutions.
\end{v2quote}

\subsubsection{Computation of the Element Coordinate System}

\begin{v2quote}
We specify a local Cartesian coordinate system per element based upon the (simplified) barycenter.
Say we note the global coordinates $\mathbf{R} = X\mathbf{e}_x + Y\mathbf{e}_y + Z\mathbf{e}_z$.
We proceed by first computing the element barycenter $\mathbf{R}_e$ as the arithmetic mean of the
locations of the principal vertices, i.e.\ the nodes corresponding to those of the associated
linear element:
%
\begin{equation}
  \mathbf{R}_e = \frac{1}{N_\mathrm{lin}} \sum_{i=1}^{N_\mathrm{lin}} \mathbf{R}_i
\end{equation}
%
The element local coordinates are then defined as $\mathbf{r} = \mathbf{R} - \mathbf{R}_e$;
we then use the notation $\mathbf{r} = x\mathbf{e}_x + y\mathbf{e}_y + z\mathbf{e}_z$.

Correspondingly, an element-local origin of the time dimension is defined as the mid-point of the
relevant physical time slab $[T_n, T_{n+1}]$, such that
$t = T - (T_n + T_{n+1})/2$.
\end{v2quote}

\paragraph{Numerical stability: mandatory normalization.}
Using element-local but \emph{unnormalized} coordinates in monomials $x^p, y^p, z^p$ at
high orders causes catastrophic floating-point overflow or underflow when the physical
element size differs greatly from~1 (e.g.\ kilometres or micrometres).  Implementations
\emph{must} normalize the local coordinates by a characteristic element length:
\begin{equation}
  \xi = x/h^e, \quad \eta = y/h^e, \quad \zeta = z/h^e,
  \qquad
  h^e = \max_{i,j \in \{1,\ldots,N_v\}} \|\mathbf{R}_i^\mathrm{vertex} - \mathbf{R}_j^\mathrm{vertex}\|
\end{equation}
where the maximum is taken over pairs of principal vertices.  This guarantees
$\xi, \eta, \zeta \in O([-1, 1])$, well-conditioned Vandermonde matrices, and stable
reconstruction.  The characteristic length $h^e$ \emph{must} be stored alongside the modal
coefficients (typically as a per-element scalar) so a reader can recover physical values.

\subsubsection{Cartesian Modal Interpolants}

\begin{v2quote}
The interpolation space for Cartesian modal interpolations follows the same approach as for
parametric modal interpolation and is based on ordered sets of monomials spanning the standard
Pascal spaces.  Here these are monomials in the element-local Cartesian coordinates $x, y, z$
and (physical) time $t$, rather than coordinates in parametric space and time.  The ordered sets
of monomials for a purely spatial interpolation are thus given by:
\end{v2quote}

\begin{v2quote}
\begin{itemize}
  \item 1D: the monomials $1, x, x^2, x^3, \ldots, x^p$

  \item 2D --- Pascal triangle ordered as:
\begin{lstlisting}[language=C,numbers=none]
for (int i=0; i<=p; i++)
    for (int j=0; j<=i; j++)
        f[idx++] = x^(i-j) * y^j;
\end{lstlisting}

  \item 3D --- Pascal tetrahedron ordered as:
\begin{lstlisting}[language=C,numbers=none]
for (int i=0; i<=p; i++)
    for (int j=0; j<=i; j++)
        for (int k=0; k<=i-j; k++)
            f[idx++] = x^(i-j-k) * y^k * z^j;
\end{lstlisting}
\end{itemize}

A space-time interpolation can be obtained by multiplying with temporal monomials:

\begin{itemize}
  \item 1D in space plus time:
\begin{lstlisting}[language=C,numbers=none]
for (int h=0; h<=q; h++)
    for (int i=0; i<=p; i++)
        f[idx++] = t^h * x^i;
\end{lstlisting}

  \item 2D in space plus time:
\begin{lstlisting}[language=C,numbers=none]
for (int h=0; h<=q; h++)
    for (int i=0; i<=p; i++)
        for (int j=0; j<=i; j++)
            f[idx++] = t^h * x^(i-j) * y^j;
\end{lstlisting}

  \item 3D in space plus time:
\begin{lstlisting}[language=C,numbers=none]
for (int h=0; h<=q; h++)
    for (int i=0; i<=p; i++)
        for (int j=0; j<=i; j++)
            for (int k=0; k<=i-j; k++)
                f[idx++] = t^h * x^(i-j-k) * y^k * z^j;
\end{lstlisting}
\end{itemize}
\end{v2quote}

% ─────────────────────────────────────────────────────────────────────────
\subsubsection{\texttt{ElementInterpolation\_t} --- New SIDS Section~12.10}
\label{sec:element-interpolation}
% ─────────────────────────────────────────────────────────────────────────

\begin{v2quote}
The \texttt{ElementInterpolation\_t} specifies the geometric interpolation of an element by
listing an alternative set of Lagrange high-order control points in parametric space following
the element conventions for the coordinate system.  In the absence of such a block for a given
\texttt{ElementType\_t}, the standard described in Section~\ref{sec:coord-systems} is followed.  It is assumed that
the first points correspond to the principal vertices of the corresponding linear element, in the
same order (cf.\ Figure~\ref{fig:coord-systems}).
\end{v2quote}

\begin{sidsnode}{ElementInterpolation\_t :=}
ElementType\_t Element;                                  \textrm{(r)}\\
DataArray\_t<Float,DataSize[]> LagrangeControlPoints;    \textrm{(o)}\\
DataArray\_t<Float,DataSize[]> MonomialCoefficients;     \textrm{(o)}\\
\};
\end{sidsnode}

The interpolation type is not stored explicitly as a child node; it is inferred from
which optional children are present:
\begin{itemize}
  \item \texttt{LagrangeControlPoints} present $\Rightarrow$ \texttt{ParametricLagrange}
  \item \texttt{MonomialCoefficients} present $\Rightarrow$ \texttt{ParametricMonomialsPascal}
  \item neither present $\Rightarrow$ \texttt{IsoParametric} (element's own coordinates used)
\end{itemize}
\texttt{CartesianMonomialsPascal} applies to \emph{solution} interpolation only and cannot
be attached to an \texttt{ElementInterpolation\_t} node.

\begin{v2quote}
\textbf{Limitations}: The current proposal maintains \texttt{ElementType\_t} to describe both
element type and geometric order, meaning we cannot go beyond 4th-order interpolation.  This
choice is motivated by maintaining the \texttt{ElementConnectivity\_t} leaf in its current shape
and the fact that currently there is no real need for higher geometric orders.
\end{v2quote}

\paragraph{Uniqueness.}
At most one \texttt{ElementInterpolation\_t} per exact \texttt{ElementType\_t} tag is permitted
within a family.  Tags differing only in geometric order are considered distinct; for example a
single family may carry separate \texttt{QUAD\_4} and \texttt{QUAD\_9} \texttt{ElementInterpolation}
nodes.  The constraint is enforced both on write and on read.

\subsubsection{Changes in Section~7.3 (\texttt{Elements\_t})}
% ─────────────────────────────────────────────────────────────────────────

\begin{v2quote}
In case an alternative location for the element control points is specified, the actual elements
are defined as before by listing the indices in the coordinate table, with the notable change that
the order will correspond to the control point coordinates specified in the corresponding
\texttt{ElementInterpolation\_t} block.  If a specific element type is not found among these
leaves, the standard convention is applied.
\end{v2quote}

% ─────────────────────────────────────────────────────────────────────────
\subsubsection{\texttt{SolutionInterpolation\_t} --- New SIDS Section~12.11}
\label{sec:solution-interpolation}
% ─────────────────────────────────────────────────────────────────────────

\begin{v2quote}
The interpolation functions associated to the interpolation on a given element type and order
are stored in a \texttt{SolutionInterpolation\_t} leaf attached to the corresponding Family.
\end{v2quote}

\begin{sidsnode}{SolutionInterpolation\_t :=}
ElementType\_t Element;                                  \textrm{(r)}\\
Integer SpatialOrder;                                    \textrm{(r)}\\
Integer TemporalOrder;                                   \textrm{(o/d)}\\
InterpolationType\_t InterpolationName;                  \textrm{(r)}\\
DataArray\_t<Float,DataSize[]> LagrangeControlPoints;    \textrm{(o)}\\
DataArray\_t<Float,DataSize[]> MonomialCoefficients;     \textrm{(o)}\\
\};
\end{sidsnode}

\paragraph{Uniqueness and lookup.}
At most one \texttt{SolutionInterpolation\_t} per (basic-element-type, \texttt{SpatialOrder},
\texttt{TemporalOrder}) triplet is permitted within a family.  Lookup is bidirectional with
fallback: a query for triplet $(\texttt{TETRA\_10}, 2, 0)$ first searches for an exact
\texttt{TETRA\_10} match and, if absent, falls back to the basic-element tag \texttt{TETRA\_4}.
This permits a single basis description to cover all geometric orders of the same element family.

\begin{v2quote}
The relevant \texttt{SolutionInterpolation\_t} block will be found using the pair composed by
the (basic) element type and interpolation order.  The former corresponds to either the actual
element tag or, if the corresponding \texttt{SolutionInterpolation\_t} block is absent, the type
of the corresponding linear element.  For instance, the interpolation functions for the 2nd-order
solution on a 4th-order tetrahedron will be associated to element tag \texttt{TETRA\_35} or
\texttt{TETRA\_4}.  Finally, if \texttt{InterpolationName} is not specified, standard
interpolation (i.e.\ constant per element) applies.
\end{v2quote}

\subsubsection{Addition to Section~7.7 (\texttt{FlowSolution\_t})}
\label{sec:flowsolution}
% ─────────────────────────────────────────────────────────────────────────

\begin{v2quote}
In case variable high-order solutions are stored, a separate solution block per interpolation
order in space (and time) should be stored.  The interpolation orders attached to the zone are
indicated by the integers \texttt{SpatialOrder} and \texttt{TemporalOrder}.  The location of
the solution is then supposed to be \texttt{CellCenter}, and in case of a variable-order

\begin{v2quote}
The default value for \texttt{SpatialOrder} depends on the type of interpolation; the default
for \texttt{TemporalOrder} is~0.
\end{v2quote}

\noindent\textbf{Implementation note 1 --- Storage of orders.}
Although the SIDS prose above lists \texttt{SpatialOrder} and \texttt{TemporalOrder} as scalar
fields of \texttt{FlowSolution\_t}, the normative on-disk encoding stores them as a single
\texttt{IndexArray\_t} child node named \texttt{InterpolationOrders} of dimension~2, with values
\texttt{[spatialOrder, temporalOrder]}.  This is the form described in
Section~\ref{sec:filemap} and implemented by
\texttt{cg\_sol\_interpolation\_order\_read/write}.

\noindent\textbf{Implementation note 2 --- Grid location convention.}
For high-order solutions covering an entire zone (the standard case), the
\texttt{GridLocation} field is \texttt{InterpolationPoints}
(see~Section~\ref{sec:interpolation-points-loc}).  For variable-order configurations using
\texttt{PointRange} or \texttt{PointList} subsets, \texttt{GridLocation = CellCenter} is used
and the per-subset orders are recorded in the \texttt{InterpolationOrders} child of each
\texttt{FlowSolution\_t} block.

\begin{v2quote}
The family contains the set of interpolation bases:
\begin{itemize}
  \item for elements as a function of the element type \texttt{ElementType\_t};
  \item for the solution as a function of the combination \texttt{ElementType\_t} and two
    interpolation orders \texttt{os} and \texttt{ot}.  This means that no more than one
    specification can be present for the triplet $(t, \texttt{os}, \texttt{ot})$.  The element
    type always refers back to the baseline element, i.e.\ the solution interpolation basis for
    the triplets (\texttt{TETRA\_4},4,0) and (\texttt{TETRA\_10},4,0) are the same;
  \item the number of coordinates of the control points is defined by the dimension associated
    to the element type.
\end{itemize}
\end{v2quote}

\paragraph{IsoParametric mesh interpolation.}
\texttt{cg\_element\_isoparametric\_write} is a convenience writer that creates an
\texttt{ElementInterpolation\_t} node with neither \texttt{LagrangeControlPoints} nor
\texttt{MonomialCoefficients}.  The interpolation type is implicitly
\texttt{IsoParametric}: the element's own connectivity table coordinates are reused, and no
control-point write call follows.  The corresponding read function
\texttt{cg\_element\_interpolation\_points\_read} returns \texttt{CG\_NODE\_NOT\_FOUND} on such
nodes.

\paragraph{Modal coefficient access.}
\texttt{cg\_element\_interpolation\_coefficients\_\{read,write\}} and the matching
\texttt{cg\_solution\_interpolation\_coefficients\_\{read,write\}} pair operate on the
\texttt{MonomialCoefficients} child.  The expected array length is given by
\texttt{cg\_element\_monomial\_size} or \texttt{cg\_solution\_monomial\_size}.  These functions
must not be called on a node whose interpolation type is \texttt{ParametricLagrange} or
\texttt{IsoParametric}.

\section{Implementation Specification}
\label{sec:impl-spec}
%% ═════════════════════════════════════════════════════════════════════════

This section consolidates the formal constraints, on-disk encodings, error semantics, and
default values that a conforming implementation must observe.  It applies to both readers and
writers.

% ─────────────────────────────────────────────────────────────────────────
\subsection{Polynomial Order Limits}
% ─────────────────────────────────────────────────────────────────────────

\begin{itemize}
  \item \textbf{Geometric order} (encoded via \texttt{ElementType\_t}): bounded by the available
    high-order tags, currently up to fourth order (e.g.\ \texttt{HEXA\_125}, \texttt{TETRA\_35}).
  \item \textbf{Solution spatial order}: integer in $[1, 1000]$.  Order $0$ is reserved as a
    sentinel for ``no high-order solution'' and is rejected by the strict CPEX-0045 validation.
  \item \textbf{Solution temporal order}: integer $\ge 0$.
  \item \textbf{Recommended ranges} (warning thresholds in \texttt{cgnscheck}): spatial
    $[1,100]$, temporal $[0,10]$.  Values outside these ranges are accepted but flagged for
    human review.
  \item \textbf{Constraint}: \texttt{TemporalOrder} $> 0$ requires \texttt{SpatialOrder} $\ge 1$.
\end{itemize}

% ─────────────────────────────────────────────────────────────────────────
\subsection{On-Disk Layout of Control Points and Coefficients}
\label{sec:on-disk-layout}
% ─────────────────────────────────────────────────────────────────────────

\paragraph{LagrangeControlPoints (purely spatial).}
The data array is stored as a 2D \texttt{R8} array with shape
$[\textit{Dim}, \textit{NPoints}]$ in CGNS (Fortran-style) ordering, i.e.\ \textit{Dim} is the
fast-varying axis and \textit{NPoints} the slow-varying axis.  Equivalently, the byte stream is
the concatenation of $\texttt{NPoints}$ tuples, each of length \textit{Dim}:
\begin{equation*}
  (u_0, v_0, w_0,\; u_1, v_1, w_1,\; \ldots,\; u_{N-1}, v_{N-1}, w_{N-1})
\end{equation*}

\paragraph{LagrangeControlPoints (space-time).}
\begin{sloppypar}
For \texttt{SolutionInterpolation\_t} with $\texttt{TemporalOrder} > 0$, the array shape becomes
$[\textit{Dim}+1,\, \textit{NPoints}_\mathrm{ST}]$ where
$\textit{NPoints}_\mathrm{ST} = \textit{NPoints}_\mathrm{spatial} \times (q+1)$
and $q = \texttt{TemporalOrder}$.  Within each coordinate row, the points are ordered
\emph{time-major}:
\end{sloppypar}
\begin{equation*}
  \texttt{idx} = t \times N_\mathrm{spatial} + s,
  \qquad t = 0, \ldots, q,
  \qquad s = 0, \ldots, N_\mathrm{spatial}-1
\end{equation*}
That is, all spatial points at time level $t=0$ are listed first, then all spatial points at
$t=1$, and so on.  The first \textit{Dim} rows of the $[\textit{Dim}+1, \cdot]$ array store
$u, v, w$; the last (Dim+1)-th row stores the parametric time $\tau$.  Equivalently, the
spatial coordinate components $u, v, w$ for all points are written first (the
\textit{Dim}-fast layout), and the entire temporal $\tau$ array follows as a contiguous
trailing block.  Solution-data arrays in \texttt{FlowSolution\_t} for space-time interpolation
follow the same time-major ordering within each element's $N_\mathrm{DOFs/element}$ block.

\paragraph{MonomialCoefficients.}
A 1D \texttt{R8} array of length $N_\mathrm{modal} = \binom{p+d}{d}$ for purely spatial
interpolation, or $N_\mathrm{modal}\times(q+1)$ for space-time, where $d$ is the element
dimension, $p$ is the spatial order, and $q$ is the temporal order.  The Pascal-traversal order
is given by the loops in Section~\ref{sec:parametric-modal} and is a writer convention; the
library does not validate ordering.

\paragraph{InterpolationOrders.}
A 1D \texttt{IndexArray\_t} (data type \texttt{I4}) of length~2, child of
\texttt{FlowSolution\_t}, holding $[\texttt{spatialOrder}, \texttt{temporalOrder}]$.  Recognized
only for \texttt{Unstructured} zones.

\paragraph{High-order \texttt{FlowSolution\_t} field arrays.}
When \texttt{GridLocation = InterpolationPoints}, each field \texttt{DataArray\_t} child of
\texttt{FlowSolution\_t} has length
$N_\mathrm{elements} \times N_\mathrm{DOFs/element}$.
Within the array, all DOFs of element~0 are stored contiguously, followed by all DOFs of
element~1, and so on:
\begin{equation*}
  \text{array index} \;=\; e \times N_\mathrm{DOFs} + \mathit{local\_dof\_index}
\end{equation*}
where $e$ is the 0-based element index and $\mathit{local\_dof\_index}$ runs from $0$ to
$N_\mathrm{DOFs}-1$ in the ordering established by the associated
\texttt{SolutionInterpolation\_t} (Lagrange control points listed in
\texttt{LagrangeControlPoints}, or modal coefficients in the Pascal traversal of
Section~\ref{sec:parametric-modal}).

% ─────────────────────────────────────────────────────────────────────────
\subsection{Validation Requirements (Reader)}
% ─────────────────────────────────────────────────────────────────────────

A conforming reader must reject:
\begin{itemize}
  \item \texttt{ElementInterpolation\_t} payloads that are not \texttt{I4} scalar (the
    \texttt{ElementType\_t} value);
  \item \texttt{SolutionInterpolation\_t} payloads that are not \texttt{I4}, dimension~1, with
    \texttt{dim\_vals[0] = 3} (the triple
    $[\textit{ElementType}, \textit{SpatialOrder}, \textit{TemporalOrder}]$);
  \item \texttt{LagrangeControlPoints} children whose data type is not \texttt{R8} or whose
    array dimension is not~2;
  \item \texttt{MonomialCoefficients} children whose data type is not \texttt{R8} or whose
    array dimension is not~1;
  \item \texttt{DataArray\_t} children of \texttt{ElementInterpolation\_t} or
    \texttt{SolutionInterpolation\_t} whose name is anything other than
    \texttt{LagrangeControlPoints} or \texttt{MonomialCoefficients};
  \item \texttt{SolutionInterpolation\_t} nodes that do not contain exactly one
    \texttt{InterpolationType\_t} child named \texttt{InterpolationType};
  \item Duplicate \texttt{ElementInterpolation\_t} nodes (same \texttt{ElementType\_t} tag) or
    duplicate \texttt{SolutionInterpolation\_t} nodes (same basic-type, \texttt{os},
    \texttt{ot}) within a family.
\end{itemize}

% ─────────────────────────────────────────────────────────────────────────
\subsection{Cross-Validation Rules (Writer)}
% ─────────────────────────────────────────────────────────────────────────

{\sloppy
\begin{itemize}
  \item \texttt{cg\_solution\_interpolation\_points\_write} must be rejected when the
    parent \texttt{SolutionInterpolation\_t} has \texttt{InterpolationType} of
    \texttt{ParametricMonomialsPascal} or \texttt{CartesianMonomialsPascal} (modal nodes do not
    carry Lagrange points; coefficients must be written instead).
  \item \texttt{cg\_element\_isoparametric\_write} must not be followed by
    \texttt{cg\_element\_interpolation\_points\_write} or
    \texttt{cg\_element\_interpolation\_coefficients\_write} on the same node.
  \item Re-writing an existing \texttt{LagrangeControlPoints} or \texttt{MonomialCoefficients}
    array requires the file to be opened in \texttt{CG\_MODE\_MODIFY}; in
    \texttt{CG\_MODE\_WRITE} the second write must be rejected.
  \item \texttt{cg\_sol\_interpolation\_order\_write} must reject grid locations other than
    \texttt{InterpolationPoints} or \texttt{CellCenter}, and must require an existing
    \texttt{PointRange} or \texttt{PointList} on the parent \texttt{FlowSolution\_t} when
    \texttt{GridLocation} = \texttt{CellCenter}.
\end{itemize}
\par}

% ─────────────────────────────────────────────────────────────────────────

\begin{itemize}
  \item \texttt{SolutionInterpolation\_t}: \texttt{SpatialOrder} is required (no default);

  \item \texttt{FlowSolution\_t.InterpolationOrders}: when the child is absent
    \texttt{cg\_sol\_interpolation\_order\_read} returns \texttt{CG\_NODE\_NOT\_FOUND} with

    (non-high-order) solution.
\end{itemize}

% ─────────────────────────────────────────────────────────────────────────
\subsection{Coordinate-System Conventions}
% ─────────────────────────────────────────────────────────────────────────

The natural parametric domains for the supported elements (illustrated in
Figure~\ref{fig:coord-systems}) are conventional:
\begin{itemize}
  \item Tensor-product elements (\texttt{BAR}, \texttt{QUAD}, \texttt{HEXA}): unit cube
    $[-1, 1]^d$.
  \item Simplex elements (\texttt{TRI}, \texttt{TETRA}): unit simplex $\{u_i \ge 0,\;
    \sum u_i \le 1\}$.
  \item Prism (\texttt{PENTA}): triangular cross-section in $(u,v) \in \{u,v \ge 0,\;
    u+v \le 1\}$ extruded along $w \in [-1, 1]$.
  \item Pyramid (\texttt{PYRA}): see~\cite{BCD10}.
\end{itemize}
The library does \emph{not} enforce these ranges on user-supplied control points; any
\texttt{double} value is accepted.  Conformance with the conventional domain is the writer's
responsibility.

\subsection{Scope of \texttt{InterpolationPoints} Grid Location}
% ─────────────────────────────────────────────────────────────────────────

{\sloppy
\texttt{GridLocation\_t = InterpolationPoints} is valid only on \texttt{FlowSolution\_t} nodes.
\texttt{ArbitraryGridMotion\_t} and \texttt{DiscreteData\_t} nodes must not use this location.
\par}


%% ═════════════════════════════════════════════════════════════════════════
\section{Variable-Order Configurations and IsoParametric Solutions}
\label{sec:variable-order}
%% ═════════════════════════════════════════════════════════════════════════

This section describes the three usage patterns that arise when different cells or different
field variables require different polynomial orders, and the use of \texttt{IsoParametric}
for solution interpolation.

% ─────────────────────────────────────────────────────────────────────────
\subsection{Variable Order Per Cell (Disjoint \texttt{PointRange})}
% ─────────────────────────────────────────────────────────────────────────

When different subsets of cells use different polynomial orders, create one
\texttt{FlowSolution\_t} block per subset using \texttt{cg\_sol\_ptset\_write} with
non-overlapping \texttt{PointRange} intervals, each annotated with
\texttt{cg\_sol\_interpolation\_order\_write}:

\begin{lstlisting}[language=C,basicstyle=\ttfamily\small]
/* Cells 1..4 at order 2, cells 5..8 at order 3 */
cgsize_t range_lo[2]={1,1}, range_hi[2]={4,1};
cg_sol_ptset_write(fn,B,Z,"FS_p2",CellCenter,PointRange,2,range_lo,&S1);
cg_sol_interpolation_order_write(fn,B,Z,S1, 2,0);

cgsize_t range_lo2[2]={5,1}, range_hi2[2]={8,1};
cg_sol_ptset_write(fn,B,Z,"FS_p3",CellCenter,PointRange,2,range_lo2,&S2);
cg_sol_interpolation_order_write(fn,B,Z,S2, 3,0);
\end{lstlisting}

% ─────────────────────────────────────────────────────────────────────────
\subsection{Variable Order Per Cell (\texttt{PointList})}
% ─────────────────────────────────────────────────────────────────────────

Non-contiguous subsets require \texttt{PointList} instead of \texttt{PointRange}:

\begin{lstlisting}[language=C,basicstyle=\ttfamily\small]
cgsize_t odd[4]  = {1,3,5,7};
cgsize_t even[4] = {2,4,6,8};
cg_sol_ptset_write(fn,B,Z,"FS_Odd", CellCenter,PointList,4,odd, &S1);
cg_sol_interpolation_order_write(fn,B,Z,S1, 2,0);
cg_sol_ptset_write(fn,B,Z,"FS_Even",CellCenter,PointList,4,even,&S2);
cg_sol_interpolation_order_write(fn,B,Z,S2, 3,0);
\end{lstlisting}

% ─────────────────────────────────────────────────────────────────────────
\subsection{Variable Order Per Field Variable}
% ─────────────────────────────────────────────────────────────────────────

When different physical fields use different polynomial orders over the \emph{same} set of
cells, create one \texttt{FlowSolution\_t} per field variable with the same \texttt{PointRange}
but distinct interpolation orders:

\begin{lstlisting}[language=C,basicstyle=\ttfamily\small]
cgsize_t all[2] = {1, N_ELEM};
/* Density at order 2 */
cg_sol_ptset_write(fn,B,Z,"FS_Density",CellCenter,PointRange,2,all,&S1);
cg_sol_interpolation_order_write(fn,B,Z,S1, 2,0);
cg_field_write(fn,B,Z,S1,RealDouble,"Density",density,&fld);

/* VelocityX at order 3 */
cg_sol_ptset_write(fn,B,Z,"FS_VelocityX",CellCenter,PointRange,2,all,&S2);
cg_sol_interpolation_order_write(fn,B,Z,S2, 3,0);
cg_field_write(fn,B,Z,S2,RealDouble,"VelocityX",velocity,&fld);
\end{lstlisting}

% ─────────────────────────────────────────────────────────────────────────
\subsection{\texttt{IsoParametric} for \texttt{SolutionInterpolation\_t}}
% ─────────────────────────────────────────────────────────────────────────

When \texttt{InterpolationName} is set to \texttt{IsoParametric}, the solution uses the
same interpolation basis as the mesh (i.e.\ the \texttt{ElementInterpolation\_t} defined for
the same element type in the family).  No \texttt{LagrangeControlPoints} or
\texttt{MonomialCoefficients} child is stored.  The corresponding
\texttt{ElementInterpolation\_t} must exist in the family.

\begin{lstlisting}[language=C,basicstyle=\ttfamily\small]
int sn;
cg_solution_interpolation_write(fn,bn,fam,"QUAD4_IsoParam",
    QUAD_4, /*os=*/1, /*ot=*/0, IsoParametric, &sn);
/* No cg_solution_interpolation_points_write call needed */
\end{lstlisting}

Reading back verifies that \texttt{cg\_solution\_interpolation\_points\_read} returns
\texttt{CG\_NODE\_NOT\_FOUND} for an \texttt{IsoParametric} node.


%% ═════════════════════════════════════════════════════════════════════════
\section{Compliance Tests}
\label{sec:compliance}
%% ═════════════════════════════════════════════════════════════════════════

A conforming implementation must pass the following objective tests.  These are independent
of any particular library and can be applied directly to a written file.

\paragraph{Partition of unity (Lagrange).}
For \texttt{ParametricLagrange} interpolation of any supported element type and order $p$,
\begin{equation}
  \sum_{i=1}^{N} \lambda_i(\mathbf{u}) = 1
  \quad \text{for any } \mathbf{u} \text{ in the parametric domain},
\end{equation}
within tolerance $\epsilon = 10^{-12}$.  Reference test points: \texttt{QUAD} $p=2$ at
$(u,v)=(0.3, -0.7)$; \texttt{HEXA} $p=2$ at $(0.5, -0.5, 0.2)$; \texttt{TRI} $p=2$ at
$(-0.5, -0.3)$; \texttt{TETRA} $p=2$ at $(-0.6, -0.2, -0.1)$.

\paragraph{Kronecker delta (Lagrange).}
At each control point $\mathbf{u}_j$,
\begin{equation}
  \lambda_i(\mathbf{u}_j) = \delta_{ij}
\end{equation}
within tolerance $10^{-12}$ for all $i, j \in \{1, \ldots, N\}$.

\paragraph{Modal coefficient ordering.}
Represent a known polynomial in the chosen modal basis and verify that the resulting
coefficient vector matches the expected ordering of Section~\ref{sec:parametric-modal}
(parametric Pascal traversal) or Section~\ref{sec:cartesian-modal} (Cartesian column-major).
For example, the polynomial $f(u,v) = u^2 + v$ over a \texttt{QUAD} $p=2$ Cartesian modal
basis must produce a coefficient vector whose only non-zero entries are
$c[u^2 v^0] = 1$ and $c[u^0 v^1] = 1$; if the indices of those non-zero entries differ from
the convention, the implementation is non-compliant.

\paragraph{Geometry reconstruction.}
For a curved \texttt{QUAD\_9} element with the centre node displaced from its parametric
midpoint, evaluating the interpolated geometry at $(u,v)=(0,0)$ must reproduce the displaced
centre coordinates within tolerance $10^{-10}$.

\paragraph{Numerical stability (Cartesian modal).}
For a \texttt{QUAD} element whose physical extents span large or small scales (e.g.\
$10^{6}$ or $10^{-6}$ in either coordinate), modal-coefficient writes followed by reads
must round-trip the data without overflow or precision loss when the implementation applies
the normalization of Section~\ref{sec:cartesian-modal}.  Failure of this test indicates
missing or incorrect normalization.

\paragraph{Compliance checklist.}
\begin{itemize}
  \item Partition-of-unity test for every supported element type and order.
  \item Kronecker delta property at every control point.
  \item Modal-coefficient ordering matches Pascal traversal (parametric) or column-major
    tensor product (Cartesian).
  \item Geometry reconstruction within tolerance $10^{-10}$.
  \item Numerical stability for extreme coordinate scales.
  \item Time-major ordering for space-time data layout.
  \item Principal vertices identified per the linear sub-element rule (Cartesian modal only).
  \item Coordinate normalization applied for Cartesian modal interpolation.
  \item \texttt{LagrangeControlPointDistribution} attribute present on every
    \texttt{ParametricLagrange} node.
\end{itemize}

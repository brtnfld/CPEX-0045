\section{Purpose of This Document}
%% ═════════════════════════════════════════════════════════════════════════

CPEX-0045 v2 was approved by the Steering Committee and established the SIDS structure for
high-order polynomial interpolation.  This package requests adoption of \textbf{v3} as a
revision to that approved proposal.

Because v2 is already approved, the committee is asked only to evaluate the \emph{delta}
described in Section~\ref{sec:changes}.  The full v3 document (CPEX-0045 v3.0, \today) is
the normative reference and is available in the repository at
\url{https://github.com/brtnfld/CPEX-0045}.  The full v3 text clearly marks all passages
reproduced from v2 with a blue left-rule callout, making the boundary between approved and new
material visually unambiguous.

%% ═════════════════════════════════════════════════════════════════════════
\section{What v2 Approved}
%% ═════════════════════════════════════════════════════════════════════════

The approved v2 established:
\begin{itemize}
  \item Two new SIDS node types: \texttt{ElementInterpolation\_t} and
    \texttt{SolutionInterpolation\_t}, both children of \texttt{Family\_t}.
  \item Three interpolation types: \texttt{ParametricLagrange},
    \texttt{ParametricMonomialsPascal}, \texttt{CartesianMonomialsPascal}, and
    \texttt{IsoParametric} (the \texttt{InterpolationType\_t} enum).
  \item Support for both purely spatial and space-time interpolation via separate
    \texttt{SpatialOrder} and \texttt{TemporalOrder} fields.
  \item Use of existing \texttt{FlowSolution\_t} for storing high-order solution data, with
    \texttt{GridLocation = CellCenter} and polynomial orders recorded in the node.
  \item Scope restricted to unstructured mesh computations.
\end{itemize}

%% ═════════════════════════════════════════════════════════════════════════
\section{Changes from v2 to v3}
\label{sec:changes}
%% ═════════════════════════════════════════════════════════════════════════

Each item is labelled \NEW{} (genuinely new content requiring a vote) or
\CLARIFY{} (formalises v2 intent; no semantic change to the approved standard).

% ─────────────────────────────────────────────────────────────────────────
\subsection{SIDS Changes}

\begin{enumerate}[leftmargin=1.5em]

  \item \NEW{} \textbf{\texttt{LagrangeControlPointDistribution\_t} enum.}
  A new enum recording the parametric-space distribution of Lagrange control points.
  Values: \texttt{GaussLobattoLegendre}, \texttt{Equidistant}, \texttt{GaussLegendre},
  \texttt{WarpAndBlend}.  Stored as an optional \texttt{DataArray\_t} child of
  \texttt{ElementInterpolation\_t} or \texttt{SolutionInterpolation\_t} named
  \texttt{LagrangeControlPointDistribution}.  Required when
  \texttt{InterpolationType = ParametricLagrange}; absent otherwise.
  \textit{Rationale:} Without this, a reader cannot reconstruct basis functions from
  control-point positions alone when standard distributions are used.  The four values cover
  all distributions in active use; \texttt{UserDefined} covers extensions.

  \item \CLARIFY{} \textbf{\texttt{GridLocation = InterpolationPoints}.}
  v2 described storing high-order solutions but did not specify a \texttt{GridLocation}
  value for the non-p-adaptive (whole-zone) case.  v3 designates
  \texttt{InterpolationPoints} as the required value when all elements in the zone share the
  same order.  \texttt{CellCenter} with \texttt{PointRange}/\texttt{PointList} remains the
  convention for variable-order (p-adaptive) configurations as implied by v2.

  \item \CLARIFY{} \textbf{\texttt{InterpolationOrders} child of \texttt{FlowSolution\_t}.}
  v2 described \texttt{SpatialOrder} and \texttt{TemporalOrder} as scalar fields of
  \texttt{FlowSolution\_t}.  v3 formalises the on-disk encoding: a single 2-element
  \texttt{IndexArray\_t} node named \texttt{InterpolationOrders} holding
  \texttt{[spatialOrder, temporalOrder]}.  This is a naming/encoding clarification; the
  information content is identical to v2.

  \item \NEW{} \textbf{Mandatory coordinate normalisation for Cartesian modal.}
  v2 defined Cartesian modal interpolation but did not specify numerical stability
  requirements.  v3 mandates that implementations normalise local Cartesian coordinates by
  the maximum inter-vertex distance $h^e$, and store $h^e$ alongside the modal coefficients.
  \textit{Rationale:} High-order monomials in physical coordinates diverge catastrophically
  at large or small element sizes; this requirement is a necessary correctness condition.

\end{enumerate}

% ─────────────────────────────────────────────────────────────────────────
\subsection{Mid-Level Library (MLL) API --- New Section}

\NEW{} v2 contained no MLL specification.  v3 adds a complete API section covering:

\begin{itemize}[nosep]
  \item Helper functions: interpolation space size queries
    (\texttt{cg\_element\_lagrange\_interpolation\_size}, etc.).
  \item Family-level read/write functions for \texttt{ElementInterpolation\_t} and
    \texttt{SolutionInterpolation\_t} nodes, including control points and modal
    coefficients.
  \item \texttt{FlowSolution\_t} point-set and order functions
    (\texttt{cg\_sol\_interpolation\_order\_read/write}).
  \item \texttt{cg\_element\_interpolation\_distribution\_read/write} and
    \texttt{cg\_solution\_interpolation\_distribution\_read/write} for
    \texttt{LagrangeControlPointDistribution\_t}.
  \item Fortran~2003 \texttt{BIND(C)} bindings for all functions.
\end{itemize}

The MLL API section is \emph{normative}: it defines the calling interface, argument types,
and error semantics that any conforming CGNS library must expose.

% ─────────────────────────────────────────────────────────────────────────
\subsection{SIDS File Mapping --- New Section}

\NEW{} v2 contained no file-mapping specification.  v3 adds a normative section
specifying the exact on-disk encoding:

\begin{itemize}[nosep]
  \item Array shapes and data types for \texttt{LagrangeControlPoints} and
    \texttt{MonomialCoefficients} (including space-time variants).
  \item Time-major ordering convention for space-time control points.
  \item Flat per-element DOF layout for \texttt{FlowSolution\_t} field arrays.
\end{itemize}

% ─────────────────────────────────────────────────────────────────────────
\subsection{Implementation Specification --- New Section}

\NEW{} v3 adds a formal implementation-specification section consolidating:

\begin{itemize}[nosep]
  \item Polynomial order limits and recommended ranges.
  \item Validation requirements for readers and writers.
  \item Error-code semantics (\texttt{CG\_OK}, \texttt{CG\_NODE\_NOT\_FOUND},
    \texttt{CG\_ERROR}).
  \item Default values for optional fields.
  \item Coordinate-system domain conventions per element type.
  \item Scope of the new \texttt{InterpolationPoints} grid location.
\end{itemize}

\section{Implementation Evidence}
%% ═════════════════════════════════════════════════════════════════════════

The v3 specification has been fully implemented in the CGNS library:

\begin{itemize}[nosep]
  \item All MLL C functions are implemented in \texttt{cgnslib.c} and declared in
    \texttt{cgnslib.h}.
  \item \texttt{LagrangeControlPointDistribution\_t} enum, name array, and accessor
    \texttt{cg\_LagrangeControlPointDistributionName} are present in the library.
  \item Internal readers (\texttt{cgns\_internals.c}) recognise all new child nodes.
  \item Fortran \texttt{BIND(C)} wrappers are implemented in \texttt{cgns\_f.F90}.
  \item \texttt{cgnscheck} validates CPEX-0045 nodes; \texttt{-s} (strict) mode promotes
    warnings to errors.
  \item C and Fortran test programs pass on the development branch.
\end{itemize}

Branch: \texttt{CPEX45\_high\_order\_wip} in the CGNS GitHub repository
(\url{https://github.com/CGNS/CGNS}).

%% ═════════════════════════════════════════════════════════════════════════
\section{Items Deferred to a Future CPEX}
%% ═════════════════════════════════════════════════════════════════════════

The following item was explicitly identified in v2 as out of scope and remains deferred:

\begin{itemize}
  \item \textbf{Explicit symbolic representation of interpolation functions.}
  Storing the actual mathematical expressions of each basis function (e.g.\ in a symbolic
  math format) would allow fully arbitrary user-defined bases beyond the four enumerated
  \texttt{LagrangeControlPointDistribution\_t} values and the fixed Pascal ordering.  This
  requires agreement on a portable expression-encoding format and is left for a future CPEX.
\end{itemize}

\section{Formal Motion}
%% ═════════════════════════════════════════════════════════════════════════

\begin{motionbox}
\textbf{Motion.}

The CGNS Steering Committee moves to adopt \textbf{CPEX-0045 version 3.0}
(dated \today) as an amendment to the previously approved CPEX-0045 v2,
incorporating the following additions to the CGNS standard:

\begin{enumerate}
  \item The \texttt{LagrangeControlPointDistribution\_t} enumerated type and its
    associated \texttt{LagrangeControlPointDistribution} child node within
    \texttt{ElementInterpolation\_t} and \texttt{SolutionInterpolation\_t}.
  \item The designation of \texttt{GridLocation = InterpolationPoints} as the required
    location for whole-zone high-order \texttt{FlowSolution\_t} nodes.
  \item The \texttt{InterpolationOrders} \texttt{IndexArray\_t} child of
    \texttt{FlowSolution\_t} as the normative on-disk encoding for interpolation orders.
  \item Mandatory coordinate normalisation by $h^e$ for Cartesian modal interpolation.
  \item The Mid-Level Library API, SIDS File Mapping, and Implementation Specification
    sections of CPEX-0045 v3.0 as normative components of the standard.
\end{enumerate}
